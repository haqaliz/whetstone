## 4. Testing strategy

- Unit tests: as above, written first.
- **Adversarial (touches the gate's input trust, not the reward):** the post-seal edit of
  `dataset_digest` must stop `run_gate` before scoring — under the old code the same edit produced a
  record naming the edited digest, so the test fails against the old code and passes against the new.
  The differential test is the guard that `sealed` cannot affect a promotion: a cheat would be to make
  an unsealed candidate promote more or less easily.
- **The gate's rule is asserted unchanged** by running the existing gate tests untouched
  (`test_gate.py`, `test_gate_cli.py` beyond aspect 1's `_record_backend`), not by new copies.
- Manual: none; no real checkpoint is read.
- Deterministic, no network, no model call.

## 5. Environment, determinism, locality

- No environment variable. No weights, no GPU, no network. Gate fixtures use the stub engine.
- **Train/held-out boundary:** this aspect changes what the gate *records* about a checkpoint, not
  what it scores or which tasks it reads. The held-out document is untouched.
- Nothing leaves the machine.

## 6. Edge cases and error handling

| Case | Outcome |
|---|---|
| Trained checkpoint, `dataset_digest` missing/malformed | `DatasetDigestUnrecorded` (unchanged text) |
| Checkpoint names no base | `CheckpointUnverified` (was `KeyError`) |
| v2 checkpoint edited after sealing | `CheckpointUnverified` before scoring; no record written |
| v1 candidate | gated as before; record says `sealed: false`; decision unaffected |
| `/2` or `/1` record read by gate, morning, honest report | refused with the old schema named; never upgraded |
| `sealed` missing, not a bool | refused, never defaulted |

The gate's default stays *don't promote*; `sealed` is information, never a condition.
